## Факты разведки (актуально на 19.11)

- `src/lib/tooltip.ts` — директива `v-tip`: пишет `data-tip`, по `pointerdown` вешает `.tip-open` на 1600 мс.
- `src/style.css:106-146` — подсказка рисуется псевдоэлементом `[data-tip]::after` (`top: calc(100% + 8px)`, `z-index: 60`).
- Директива и стили в сборке есть (`dist/assets/*` содержат `tip-open`), т.е. проблема не в «забыли задеплоить».
- `public/sw.js` — `CACHE = "gena-cache-v2"`; `install` уже делает `skipWaiting()`, `activate` — `clients.claim()` + удаление старых кешей. Значит старый shell у установленной PWA может жить до перезапуска, но версия всё равно требует бампа.
- `ChatView.vue` уже структурный порт (toolbar → stage → dock → composer), но `v-tip` есть только у части кнопок, а message actions всегда видимы (в оригинале — hover-группа).
- В оригинале подсказки — не псевдоэлемент, а **отдельный слой в `body`** (`TooltipProvider.vue`, teleport) + `useLongPressTooltip` (400 мс, вибрация 12 мс, гашение клика после долгого тапа, переворот top/bottom, clamp в вьюпорт).
- Ключевая разница: `.ai-chat-panel { overflow: hidden }` — псевдоэлементная подсказка внутри панели была бы обрезана. У gena `.chat-panel` без `overflow`, но псевдоэлемент всё равно живёт в stacking context предка и уязвим к `transform`/`backdrop-filter`/`contain` у любого родителя.

## Гипотезы, почему тултип не виден по долгому тапу (по убыванию вероятности)

1. **Псевдоэлемент не появляется визуально** — обрезка/перекрытие слоем контента или предок с `transform/filter/contain`. Симптом: `data-tip` есть, `.tip-open` появляется, `::after` не видно.
2. **Событие не доходит** — мобильный WebView (Telegram/iOS) гасит `pointerdown` из-за нативного long-press callout / выделения текста. Симптом: `.tip-open` не появляется вообще.
3. **PWA отдаёт старый бандл** — кеш `v2` живёт у установленного приложения.
4. **Кнопка `disabled`** — у disabled-элемента часть браузеров не шлёт pointer-события (актуально для «Копировать»/«Новый диалог» без сессии).

Важно: диагностика нужна только чтобы понять, чинить ли событие или слой. Перенос на отдельный слой в `body` закрывает пункты 1 и 4 независимо от причины, поэтому диагностика — короткая (этап 0), а не блокер.

3.5 **Вложения-изображения** (в scope, по фактам протокола Pico)

Разведка сервера (`pkg/channels/pico/pico.go`):

- **Отправка:** `message.send.payload.media` — строка или массив data-URL `data:image/{jpeg,png,gif,webp,bmp};base64,…`; допускается также `attachments: [{type:"image", …}]`, но элементы с `type != "image"` сервер **молча пропускает**.
- **Лимит:** 20 МБ на изображение (`DefaultMaxMediaSize`), иначе `error{code:"invalid_media"}`.
- **Приём:** `message.create.payload.attachments: [{type, url, filename, content_type}]`, где `url = "/pico/media/<refID>"` и требует auth → в `<img src>` напрямую нельзя, только `fetch` с `Authorization` → `blob:` URL.
- Вывод: обещаем **только картинки**, документы/PDF/аудио — нет (сервер их не примет).

Подшаги:

1. Композер: кнопка-скрепка (уже есть визуально) → `<input type="file" accept="image/*" multiple>`, drag&drop на stage, paste из буфера на десктопе.
2. Подготовка файла: canvas-downscale до 1600 px по длинной стороне, JPEG q0.85 (PNG с прозрачностью оставляем PNG), цель ≤ 1.5 МБ; чипы-превью над композером с удалением, максимум 5 файлов, суммарный предохранитель ≤ 4 МБ.
3. Отправка: `payload.media = [dataURL…]`; текст опционален (`empty_content` не срабатывает при наличии media).
4. Хранение: в IndexedDB кладём только миниатюру (≤ 200 px, ~20–30 КБ), полный data-URL живёт до отправки; иначе сессии раздуваются на десятки МБ.
5. Рендер: сетка 1–4 изображений в пузыре, тап → лайтбокс (fullscreen, свайп, Esc), входящие — через авторизованный `fetch` с кешем blob-URL в памяти сессии.
6. Ошибки: `invalid_media`, превышение 20 МБ, не-изображение → тост с причиной.

**Критерий:** фото с телефона (2–3 шт.) уходит и отображается в пузыре; ответ агента с картинкой показывается; перезагрузка страницы сохраняет миниатюры, не ломая квоту IndexedDB.
