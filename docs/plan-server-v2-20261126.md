# Gena Server v2 — база вместо JSON, шифрование и подключение по коду

План от 26.11.2026. Заменяет собой хранилище из `server/store.go` (файл на диалог, открытый JSON).
Версия после работ: **0.3.0**.

## 1. Что просили

1. Хранилище — не JSON-файлы, а **однофайловая защищённая БД рядом с бинарником**.
2. Структура БД **повторяет браузерную IndexedDB** (`agents`, `sessions`, `messages`, `usage`, `queue`, `tokens`, `morph`, `audit`, `servers`), чтобы клиентский код почти не переписывать.
3. **Передача между сервером и клиентом шифруется**.
4. Подключение клиента к серверу — **по коду приглашения**, в том числе **QR-кодом**.

## 2. Выбор базы: bbolt

| Вариант | Один файл | Шифрование | Чистый Go | Вывод |
|---|---|---|---|---|
| **bbolt** (etcd-io/bbolt) | да | нет, но оборачиваем значения сами | да | **берём** |
| SQLite `modernc.org/sqlite` | да | нет (SQLCipher требует cgo) | да, но +80 МБ зависимостей | запасной вариант |
| SQLite + `mattn/go-sqlite3` + SQLCipher | да | да | **нет, cgo** | ломает «один бинарник» |
| Badger / Pebble | **нет** (каталог LSM) | у Badger есть | да | мимо |

Почему bbolt подходит именно здесь:

- **Один файл** `data/gena.db` (0600) рядом с бинарником, ACID, mmap, без сервера и без cgo.
- **Семантика как у IndexedDB**: bucket = object store, ключ = `id`, значение = JSON той же формы (`keyPath` совпадает). Клиентские структуры не меняются — меняется только транспорт и место хранения.
- Индексы делаем сами отдельными bucket'ами — ровно как IDB-индексы: `idx_sessions_updated`, `idx_messages_session`.
- Размер библиотеки — сотни килобайт, а не десятки мегабайт.

Ограничение bbolt, которое надо знать: одна запись за раз (у нас один процесс — не проблема), файл не ужимается сам (добавим `gena-server compact`).

## 3. Шифрование данных на диске

- Значения шифруются **AES-256-GCM** по одному на запись: `enc:v1:<nonce><ciphertext>`, AAD = `bucket|key`. Ключи (id, время) остаются открытыми — иначе не работают индексы.
- Ключ БД: `data/keys/db.key` (32 байта, 0600), создаётся при первом старте. Переопределяется `GENA_DB_KEY_FILE`.
- Поле `content` сообщений, `title` сессий, токены агентов — внутри зашифрованного блока; просмотр возможен только через сервер.
- **Потеря ключа = потеря данных** — в README и `AGENT_INSTALL.md` явное предупреждение: бэкапить `gena.db` **и** `db.key` вместе.
- `gena-server backup <файл>` — шифрованная копия через bolt-транзакцию (без остановки сервиса).

## 4. Передача: свой слой шифрования поверх HTTP

TLS на своём сервере часто нет (LAN, IP без домена), поэтому шифруем **сами полезные данные**, не надеясь на транспорт.

- При приглашении сервер выдаёт **PSK** (32 случайных байта) внутри кода приглашения.
- Из PSK выводятся подключи через HKDF: `c2s`, `s2c`, `aad-base` (соль — `serverID`).
- Запрос: заголовки `X-Gena-Dev`, `X-Gena-TS`, `X-Gena-Nonce`; тело — `AES-256-GCM`, AAD = `method|path|ts|nonce|deviceID`. Тег GCM одновременно аутентифицирует устройство — отдельный Bearer-токен больше не нужен.
- Ответ: тело в `s2c`-ключе, свой nonce в заголовке.
- Защита от повтора: `ts` окно ±120 с, nonce запоминается на 5 минут (LRU).
- `GET /api/health` остаётся открытым, но отдаёт только `{serverId, version, enc:"v1"}` — по нему клиент проверяет адрес до подключения.
- Отзыв устройства: `gena-server device revoke <id>` → клиент получает `401 {"error":"revoked"}` и просит новый код. Ротация PSK = переподключение.

## 5. Код приглашения и QR

Код (префикс `gena1:`, JSON → base64url):

```json
{"v":1,"u":"https://host:8443","n":"Домашний сервер","sid":"<serverId>",
 "k":"<base64 PSK>","e":1794000000000,"lbl":"laptop"}
```

- **Выдача**: `gena-server invite --label laptop --ttl 15m` → печатает код, QR в терминале (ANSI), и кладёт `invite.png`. То же доступно на странице `/pair` (только с админ-токеном из `/etc/gena-server/`), чтобы отсканировать телефоном.
- **Срок**: по умолчанию 15 минут, одноразовый (после `POST /api/pair` инвайт гасится).
- **Клиент**: в «Подключения → Добавить сервер Gena» два способа — вставить код или **навести камеру** (BarcodeDetector, Chromium; иначе остаётся вставка). После пары клиент проверяет `health`, сверяет `sid` и сохраняет сервер с зашифрованным PSK (как сейчас — ключом устройства).
- Безопасность: PSK внутри QR = сам себе пароль; QR показывает тот, кто имеет доступ к серверу. Утечка QR = утечка доступа, поэтому только TTL и одноразовость.
- **Короткий код руками** (`K7F-2QW-9M4`) — опционально, отдельным решением: слабее (перебор при коротком сроке), включаем только если реально нужно.

## 6. Схема БД (повторяет IndexedDB)

```
meta                  {schema:2, serverId, createdAt}
sessions              key=id        value=JSON Session | enc:v1:…
messages              key=id        value=JSON Message | enc:v1:…
idx_sessions_updated  key=u64(updatedAt)|id        → sessionID
idx_messages_session  key=sessionID|u64(createdAt)|id → messageID
servers               key=id        (запись о самом сервере — для совместимости)
agents, usage, queue, tokens, morph, audit   (создаются пустыми: структура = IDB)
devices               key=deviceID  {id,label,pubHash,createdAt,lastSeen,revoked}   // новое
invites               key=token    {sid,label,exp,used}                            // новое
```

Поля записей — те же имена, что в `src/storage/db.ts` (`id`, `sessionId`, `createdAt`, `updatedAt`, `pinned`, `tags`, `tokenMode`, …). Благодаря этому `api.go` и клиент не меняют форматов.

## 7. Миграция и совместимость

- При старте: если БД пустая, а `data/sessions/*.json` есть — импорт всех диалогов в bbolt, каталог переименовывается в `sessions.migrated-<дата>` (не удаляем).
- Старый Bearer-токен: принимается один релиз (флаг `--legacy-token`), по умолчанию выключен. Дальше — только устройства.
- `Store` остаётся интерфейсом с теми же методами (`List, Get, Create, Patch, Delete, Append, PatchMessage, DeleteMessage, Import, Count`) — `api.go` не трогаем. Меняем реализацию на `boltStore`.

## 9. Критерии готовности

1. `data/gena.db` — единственный файл данных; `grep` по нему не находит текста сообщений.
2. Сервер стартует на пустом каталоге, мигрирует старые JSON, старые диалоги открываются в клиенте.
3. Подключение по коду: код → пара → создание сессии → сообщение → синхронизация в браузере. Отзыв устройства рвёт доступ.
4. Запрос без правильного конверта даёт 401, повтор запроса с тем же nonce — 401.
5. `go test` зелёный (включая тест «значение в файле зашифровано» и «nonce не переигрывается»), `npm test` и `vite build` зелёные.
6. В README — раздел про бэкап `gena.db` + `db.key` и про отзыв устройств.

## 10. Риски

- **Потеря `db.key`** — данные нечитаемы. Лечится только бэкапом; пишем в трёх местах документации.
- **PSK долгоживущий** — утечка устройства = доступ к серверу: отзыв + короткий TTL инвайта обязательны.
- **QR только для Chromium** (BarcodeDetector) — вставка кода остаётся основным путём.
- **bbolt-файл растёт** — раз в месяц `compact` (или по таймеру), плюс предупреждение в логе при > 200 МБ.
- **Веб-версия клиента и сервер на одном origin** — CORS уже есть, но заголовки конверта требуют `Access-Control-Allow-Headers`; не забыть.

## 11. Нужны решения (4 вопроса)

1. **bbolt** устраивает? (SQL/FTS не нужен — серверного поиска сейчас нет.)
2. Ключ БД — **файлом рядом** (просто, годится для systemd) или **спрашивать пароль при старте** (безопаснее, но сервис не поднимется без ввода)?
3. **Короткий код руками** нужен, или достаточно QR + вставки?
4. Старый Bearer-токен оставляем на один релиз для совместимости или режем сразу?
