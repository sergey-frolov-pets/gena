## 1. Пять главных проблем

**1. Стрим показывает сырой блок — тезис «половинчатый JSON невозможен» ложен.**
`finalizeConfiguredStreamingLLM` стримит финальный текст в чат *до* финализации, а вырезка делается только в `pipeline_finalize`. Значит пользователь смотрит, как набирается ```gena-ui с JSON, который потом «схлопывается» в карточку. Это ровно замечание Kimi 3, только перенесённое с парсинга на рендер. План это не закрывает ни словом — нужен скрыватель ограждения в стриме или отсечение хвоста после маркера блока при каждом дельта-кадре.

**2. Message tool и прочие пути публикации обходят Extract.**
Вырезка встроена только в финализацию хода. Но агент умеет слать через `message`-тул (`HasSentToSameChat` в `agent_outbound.go` — значит, путь реальный и активный): текст с ограждением уедет в pico и в Telegram/VK сырым, а главное — попадёт в историю и будет жечь токены, что план объявил решённым. Нужен либо Extract в message-туле, либо явный запрет блоков там.

**3. Extract противоречит сам себе и молча теряет данные.**
Три правила конфликтуют: невалидный JSON вырезаем, «не последний блок» не трогаем, при двух блоках первый остаётся в тексте и в истории. Итог: агент напечатал два блока или блок не в конце — JSON остался в истории (токены жгутся), payload не дошёл, агенту об этом никто не сказал. Следующий ход он не знает, что UI не отобразился, и не повторит. Нет ни сигнала агенту, ни метрики, ни ретрая.

**4. У карточки нет идентичности — дедуп и optimistic хрупкие.**
Нет `blockId`/корреляции между карточкой и ответом агента. Дедуп по `itemId+actionId` ломается, когда агент в новом снапшоте перегенерирует id. `disabled` снимается магическими 30 с, не связанными с реальным ходом (агент может думать дольше — пользователь тапнет повторно). Optimistic-состояние не персистится: после перезагрузки карточка снова активна, хотя действие уже ушло.

**5. `ui` живёт только в live-кадре и безвозвратно теряется.**
Сервер в историю ui не пишет (сознательно), история на клиенте — IndexedDB. Пропущенный кадр (переподключение, офлайн, второй клиент) = карточки нет никогда, recovery не предусмотрено. Дополнительно: финал доезжает несколькими путями (streaming-finalize, legacy interim publish в `pipeline_finalize.go:80+`, `PublishResponseIfNeeded`), а план цепляет ui только к одному — надо инвентаризировать все пути, иначе часть финалов придёт без ui в зависимости от того, какой веткой пошёл ход.

## 2. Что выкинуть

- **Legacy-парсинг ограждения на клиенте** (половина `ui-blocks.ts`, fallback-ветка в `MessageBody`, §5.4) — после G1 и закрытия message-тула сценарий не существует. Оставить только 20-строчный скрыватель ограждения для стрима (он нужен по п.1).
- **Ветка «kind: "ui" если придёт — тоже понять»** — прямо противоречит §8, мёртвый код.
- **Свой мини-markdown** (130 строк + XSS-тесты) — первую волну `notes.doc` сделать plain text/pre-wrap; markdown — отдельной итерацией или готовой библиотекой.
- **Новый метод `PublishResponseWithUI`** — в `outboundTurnMessageOptions` уже есть поле `raw map[string]string` (agent_utils.go:99), ui кладётся туда без нового публичного метода и без `turnResult.uiPayload`.
- **Таймер 30 с** — заменить снятием блокировки при любом новом assistant-сообщении в сессии.
- **Пресеты как отдельная сущность** на старте: захардкодить оформление в GenericView, пресеты выделить, когда появится третий плагин.

## 3. Чего не хватает

- **Проброс ui во все финальные пути:** `finalizeConfiguredStreamingLLM` (streaming-финал) и interim publish через `outboundMessageForTurnWithOptions` (`pipeline_finalize.go:80–90`) — конкретные правки не описаны.
- **Правка `pkg/tools/message*.go`:** Extract или reject ограждения в message-туле.
- **`pico-ws.ts`:** сигнатура `setFinal(id, content, attachments)` не принимает ui — нужно расширение и проброс в `TransportReply.ui` → `appendMessage`; в плане только одна строка «ui из payload → setFinal».
- **`store.ts:217`:** `appendMessage` уже имеет 6 позиционных параметров; добавление седьмого `ui?` — антипаттерн, нужен объект-опции, иначе рассинхрон вызовов.
- **Состояние:** где живёт optimistic-флаг (reactive map по messageId?), что происходит при перезагрузке, при смене сессии.
- **`blockId`** в схеме `ui` — для дедупа, корреляции действия→ответа, телеметрии.
- **Обратная связь агенту:** лог/событие при отброшенном блоке + инструкция в скилле «если блок отброшен — пришли короче».
- **`message.update` / EditMessageWithPayload:** может ли ui приехать апдейтом — поведение не определено.
- **E2E-проверка кадра:** в §6 нет теста «агент напечатал блок → кадр message.create с ui-объектом → карточка в DOM», а это единственный тест, который ловит разрыв контракта Go↔TS.

## 4. Итоговые правки плана

1. Закрыть стрим: клиентский скрыватель ```gena-ui-хвоста в дельтах; тезис Kimi 3 переформулировать.
2. Extract применить и в message-туле (или запретить блоки там) — история чистая на всех путях.
3. Унифицировать правила Extract: вырезать все gena-ui-ограждения всегда; невалидный — лог + событие агенту + метрика.
4. Убрать `PublishResponseWithUI`/`turnResult.uiPayload`, класть ui в `outboundTurnMessageOptions.raw` и пробросить во все финальные publish-ветки.
5. Ввести `blockId`; дедуп по `blockId+actionId`; optimistic-блокировка снимается новым сообщением сессии, без таймера.
6. Удалить legacy-парсинг, ветку `kind:"ui"`, свой markdown (первая волна — plain text).
7. `appendMessage` перевести на объект-опции; `setFinal`/`TransportReply` расширить ui явно.
8. Добавить E2E-тест кадра и зафиксировать решение: потерянный ui не восстанавливается, перезапрос через «покажи ещё раз».

## 5. Ответы на вопросы

**«No kind, только ключ ui» — ставка верна.** По `pico-ws.ts:354–358`: незнакомый `kind` уходит в `return` до `setFinal` — сообщение с `kind:"ui"` старый клиент потерял бы целиком, включая текст. Лишний ключ в payload старый клиент безопасно игнорирует, потому что читает payload по именам полей. Это правильный компромисс: деградация до текста вместо потери сообщения. Оговорки: (а) ветку «понять kind:"ui" на всякий случай» всё равно не нужно писать — она либо мертва, либо поощряет будущую ошибку; (б) если когда-нибудь понадобится отличать ui-сообщения по kind, сначала клиенту нужен фиче-флаг/версия, и только потом серверу kind.

**Регенерация/повторная отправка/IndexedDB — вырезка не ломает, с двумя оговорками.**
Вырезка до `AddFullMessage` — правильная точка: история агента, суммаризация, Telegram/VK получают чистый текст, токены не жгутся, регенерация безопасна (модель заново вызовет инструменты и напечатает свежий блок). IndexedDB: опциональное поле с plain object клонируется штатно, миграция не нужна, копия/поиск/TTS по чистому `content` работают без `textOnly`-костыля (кстати, тогда `ui-text.ts` на 40 строк тоже почти не нужен — он нужен только если оставляете legacy-парсинг, который я предлагаю выкинуть).
Оговорка первая: контекст карточки для модели теряется — после вырезки агент в истории видит резюме «7 задач, 3 просрочены», но не сами items; на регенерации или уточняющем вопросе («а что там третье?») он обязан заново дёрнуть инструмент. Это надо явно прописать в скилле, иначе будут галлюцинации вместо повторного вызова.
Оговорка вторая: вырезка ломает **message tool path**, а не регенерацию — если агент шлёт блок через message-тул, он минует финализацию, и блок осядет в истории. Это проблема №2 выше, и без её закрытия главное обещание плана («история чистая») не выполняется.
