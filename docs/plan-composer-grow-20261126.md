## 2. Механизм каждого дефекта

### Дефект 1 — «верх обрезан ещё до 4 строк» (height < scrollHeight)
Корень — **зеркало шире реального поля**, поэтому оно насчитывает **меньше** строк, чем реально переносится. Три источника расхождения, в сумме 1–2 px + полоса на 4 строках:

1. `fieldWidth` считается целочисленно: `box.clientWidth` (округлено) − `offsetWidth` боковых групп (округлено) − `10` (`ChatView.vue:3350`, `3319–3324`), реальное flex-поле — дробное.
2. `Math.round(width)` на входе в зеркало (`:3298`) — ещё ±0.5 px.
3. На 4 строках — полоса прокрутки (`overflow-y: auto`, `:7218`) сужает контентную ширину, зеркало её не вычитает.

Итог: `composerLinesForContent` (`composer.ts:66–80`) получает заниженную высоту контента → `lines` меньше → `composerFieldHeight` (`composer.ts:47–57`) ставит `height < scrollHeight` → верхние строки уходят в прокрутку. `4d59f72` это не закрыл: он убрал цикл раскладки, но оставил замер по вычисленной (а не фактической) ширине и без компенсации полосы.

### Дефект 2 — «дёргается на конце первой строки»
Два наложенных эффекта. (i) При переходе row→pair поле меняет ширину на ~60–90 px (`:7070–7120`) — текст перетекает, виден скачок. (ii) `Math.round(width)` + целочисленная ширина дают нестабильную точку переноса: один и тот же текст у границы строки то «влезает» в 1 строку, то переносится на 2, раскладка переключается row↔pair на соседних символах. В сумме — дрожание в момент, когда слово дописывается у правого края.

### Дефект 3 — «зависает на 3→4, поле упирается в предел»
При наборе до 4 строк: высота фиксируется на `COMPOSER_MAX_LINES=4` (`composer.ts:38`, `composerFieldHeight`), появляется полоса прокрутки (`overflow-y: auto`), контентная ширина сужается на ширину полосы (~8–15 px), текст переносится на 5-ю строку. Поле стоит на 4 строках и **прокручено** — пользователь видит «зависание» (не видно верх/новые строки). Цикла пересчётов нет (observer по ширине не срабатывает), но `watch(composerTall, () => void autoGrow())` (`:3431`) лишний раз гоняет пересчёт, не решая проблему.

## 3. Решение: как мерить строки

**Выбор: оставить зеркало, сделать его метрологически точным.**

Отказ от «мерить на реальном поле»: для замера на самом поле нужно временно менять его высоту (`height: 0` или `auto`) — это тот самый мерцающий прыжок, от которого зеркало и было введено (комментарий `:3222–3228`). К тому же реальное поле имеет ширину, зависящую от раскладки — ровно тот цикл, что убрал `4d59f72`. Зеркало вне раскладки и без побочных эффектов на видимое поле — правильная архитектура; неверна только его метрика.

Три правки в `measureComposerContent` (`ChatView.vue:3285–3300`):

1. **Убрать `Math.round`** — ставить дробную ширину: `mirror.style.width = Math.max(1, width) + "px"`. Браузер переносит по дробной ширине, как и реальное flex-поле.
2. **Вычесть резерв под полосу прокрутки.** Реальный текст переносится по `clientWidth` (контентной ширине), а она на 4 строках меньше на ширину полосы. Чтобы резерв был детерминированным (а не «появляется внезапно на 4-й строке»), добавить на textarea `scrollbar-gutter: stable` (CSS) — полоса резервируется всегда, ширина переноса постоянна на любом числе строк. Тогда `gutter = el.offsetWidth - el.clientWidth` (тот же замер, что уже делает `measureMarksGutter`, `:1930–1935`) становится константой, меряется один раз и кешируется.
3. **Передавать в зеркало контентную ширину кандидата**: `width − gutter`. Итог: зеркало переносит ровно так же, как реальное поле.

Дополнительно: зеркало копирует стили по `MIRROR_STYLE_KEYS` (`:3257–3275`) — набор уже включает `boxSizing` (глобально `border-box`, `src/style.css:58`), `padding`, `whiteSpace`, `overflowWrap`, `wordBreak`. Раз padding у поля только вертикальный (`padding: 6px 0`, `:7210`), а border 0 — контентная ширина = ширина − полоса. Ключи менять не нужно, только ширину.

**Проверка инварианта.** После установки высоты в `autoGrow` (dev-only или под `import.meta.env.DEV`): `el.scrollHeight <= el.clientHeight + 1`, иначе логировать расхождение. Это даёт ранний сигнал о любом новом источнике несовпадения.

## 4. Решение: политика ширины боковых групп

Сейчас кеш снимается один раз и навсегда (`composerSideWidths`, `:3326`). Это неверно: ширину ряда меняют микрофон (`dictationAvailable`), молния (`quickReplies.length`) и `send↔stop` (36→30 px). «Очистить»/«Свернуть» ширину не меняют (колонки), но для простоты включаем их в сигнатуру — инвалидация дешёвая и точная.

**Вариант A (выбран): инвалидация по сигнатуре набора кнопок.**
- Завести чистую функцию `composerButtonsSignature(input: { dictation: boolean; quick: boolean; sending: boolean; tall: boolean; collapsible: boolean }): string` в `composerLayout.ts` — возвращает ключ (например, склейку битов). Тестируемая.
- В `ChatView` держать `composerSideWidthsKey = ref("")`. Перед замером вычислять ключ; если изменился — сбросить `composerSideWidths = null` (переснимется в том же вызове).
- Сам `measureComposerSideWidths` (`:3311–3327`) остаётся как есть (3 переключения класса, 3 reflow), но выполняется только при реальном изменении набора кнопок, а не на каждый символ.

**Вариант B (отвергнут): мерить каждый вызов.** 3 переключения класса + 3 принудительных reflow на каждый символ — дорого на телефоне. Не нужен: ширины меняются только при изменении набора кнопок.

**Вариант C (отвергнут): константы из CSS.** 26/24/28/36/30 px дублировать в TS — рассинхронизация с CSS при будущих правках дизайна. Измерение по DOM устойчивее.

## 5. Решение: одна точка принятия решения, без watch→autoGrow и без гистерезиса

- **Одна точка:** раскладку и число строк выбирает только `resolveComposerLayout` (`composerLayout.ts:89–116`). Высота ставится ровно один раз в `autoGrow` (`:3383–3386`). Никакой другой код не пишет в `composerLines`/высоту.
- **Убрать `watch(composerTall, () => void autoGrow())`** (`:3431`). Появление «Очистить» — следствие выбора раскладки, ширину поля не меняет (колонка), повторный замер не нужен. Триггеры `autoGrow` остаются только два, оба — первичные: (1) изменение черновика (`watch(draft)`, `:3414–3427`), (2) реальное изменение ширины контейнера (`ResizeObserver` на `composerBoxEl`, `:5176–5186`).
- **Гистерезис не нужен — обоснование.** `resolveComposerLayout` — чистая функция от `(boxContentWidth, gutter, sideWidth, текст)`: результат детерминирован и монотонен по длине текста (шире поле → не больше строк). Гистерезис нужен только как костыль против нестабильности замера; после правок п.3 и п.4 нестабильности нет, и переключение 3↔4 при росте/удалении текста сходится на первом же вызове. Держать состояние-память — значит снова ввести зависимость решения от истории.
- **`ResizeObserver` оставить по ширине контейнера** (`composerBoxEl`), ранний выход по `boxWidth === composerWidth` (`:5180`) сохранить: рост высоты поля (и колонок) не должен триггерить пересчёт. С `scrollbar-gutter: stable` ширина контейнера не меняется при появлении полосы.

## 6. Пошаговый план правок

### Шаг 1. Чистый модуль `composerLayout.ts` — добавить `gutter` и сигнатуру
- `ResolveComposerLayoutInput` + `gutter: number` (резерв под полосу). В `resolveComposerLayout` замер вызывать с шириной `fieldWidthFor(...) − gutter` (не уходит в минус: `Math.max(0, …)`).
- Добавить `composerButtonsSignature(...) → string`.
- **Тесты** (`composerLayout.test.ts`):
  - с `gutter > 0` длинный текст (4+ строк) даёт `lines = 4`, а `composerFieldHeight(4) >= content`, измеренного при `fieldWidth − gutter` (регрессия дефекта 3);
  - монотонность: при росте `textPx` раскладка проходит `row→pair→column` ровно по разу, обратных переходов нет (регрессия дефекта 2);
  - `composerButtonsSignature` меняет ключ при любом из 5 флагов.

### Шаг 2. CSS — `scrollbar-gutter: stable`
- `.chat-panel__input` (`ChatView.vue:7198`): добавить `scrollbar-gutter: stable`. Перенос ширины становится постоянным на любом числе строк; `offsetWidth - clientWidth` — константа.
- Риск низкий: визуально резервируется ~8 px справа (текст не касается края), подложка подсветки уже это учитывает через `marksGutter`.

### Шаг 3. `ChatView.vue` — точный замер в `measureComposerContent`
- `:3298` — `Math.max(1, Math.round(width || el.offsetWidth || 1))` → `Math.max(1, width || el.offsetWidth || 1)` (дробная ширина, без `Math.round`).
- Передавать в функцию уже скорректированную ширину: `measureComposerContent(el, fieldWidth - gutter, padding)`.
- Замерять `gutter = el.offsetWidth - el.clientWidth` один раз (кеш в ref), по сигнатуре не сбрасывать (полоса — константа ОС, не зависит от кнопок).

### Шаг 4. `ChatView.vue` — ширина боковых групп по сигнатуре
- В `autoGrow` (`:3345–3360`): перед `composerSideWidths.value ?? measureComposerSideWidths()` вычислить `key = composerButtonsSignature({dictation: dictationAvailable, quick: quickReplies.length>0, sending: <send/stop>, tall: composerTall.value, collapsible: composerCollapsible.value})`; если `key !== composerSideWidthsKey.value` → `composerSideWidths.value = null`.
- Подставлять реальные реактивные флаги (проверить имена: `dictationAvailable`, `quickReplies`, `busy`/отправка).

### Шаг 5. `ChatView.vue` — убрать watch, зафиксировать инвариант
- Удалить `watch(composerTall, () => void autoGrow())` (`:3431`).
- В `autoGrow` после `el.style.height = nextHeight` (`:3386`) под `import.meta.env.DEV`: если `el.scrollHeight > el.clientHeight + 1` — `console.warn` с числами.

### Шаг 6. Тесты (полный набор)
- `composerLayout.test.ts` — расширить по шагу 1.
- `composer.test.ts` — добавить: `composerFieldHeight(4, …)` равен потолку; `composerLinesForContent` с `gutter`-заниженным контентом даёт ≥ реального числа строк.
- Прикладной тест (jsdom-независимый): чистый `resolveComposerLayout` с мок-`measure`, где `measure(w) = linesAt(w − gutter) * lineHeight`, — проверка, что `height >= scrollHeight` для набора текстов 1…6 строк.

### Порядок и риски
- Шаги 1–2 независимы; 3–5 зависят от 1. Каждый — отдельный коммит (на ветке `fix/composer-height`), каждый прогоняет `npx vitest run`.

## 7. Проверка вживую (Playwright)

**Где взять:** в `gena/node_modules` Playwright **нет** (`node_modules/.bin/playwright` отсутствует), Python-модуль тоже не стоит. Зато в скилле web-design уже есть Playwright-скрипты — `skills/web-design/scripts/review_site.py` (и `review_image.py`), они используют свой venv с Playwright. Проще всего: переиспользовать этот venv, либо `pip install playwright && playwright install chromium` в отдельный venv.

**Сценарий** (на `vite dev`, порт свободный, например `5174`):
1. Поднять `vite --port 5174 --strictPort`.
2. Playwright + Chromium (десктоп 1280×800) и WebKit (iPhone 13, 390×844).
3. Найти `textarea.chat-panel__input`, посимвольно печатать заранее длинную строку (~80 символов без пробелов и с пробелами).
4. После **каждого** символа логировать: `el.clientHeight`, `el.scrollHeight`, `box.dataset`/класс `is-buttons-*`, число вызовов `autoGrow` (через `page.exposeFunction`-счётчик или `console`), `offsetWidth - clientWidth` (полоса).

**Критерии:**
- `scrollHeight <= clientHeight` на **каждом** шаге (верх текста виден всегда) — закрывает дефекты 1 и 3.
- `is-buttons-*` меняется `row→pair→column` ровно по разу, без возвратов (закрывает дефект 2).
- Число вызовов `autoGrow` на символ не растёт при 3→4 (нет осцилляций; ≤ 2 вызовов на символ в норме: `watch(draft)` + один observer).
- При удалении текста обратно `column→pair→row` сходится без «мигания».
