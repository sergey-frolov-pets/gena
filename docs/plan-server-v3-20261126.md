# Gena Server v3 — SQLite, шифрование, приглашения по коду/QR, общие сессии

> **Заменён планом v4** (`plan-server-v4-20261126.md`): уточнены анонимайзер, ключ агента,
> срок доступа устройств, добавлена сущность «Проект».

План от 26.11.2026, заменяет `plan-server-v2-20261126.md` (там было bbolt и без поиска).
Релиз после работ: **0.3.0**.

## 1. Что решил Сергей (вход в план)

1. Поиск по сообщениям нужен → **SQL**, а не key-value.
2. Добавление клиента: на выбор **код**, **QR** или **код + QR**.
3. Отдельный код, если на сервере есть **агент** — чтобы добавить агента в клиент с быстрыми вставками.
4. **Анонимайзер** — отдельной галочкой; код может нести все три опции, две или одну.
5. В коде — **срок действия** и **сколько устройств** можно подключить (устройство = один пользователь). После этого срока клиент сервером не поддерживается.
6. Админ сервера может **сбросить токен клиента** вручную; на клиенте подключение удаляется вручную.
7. Сессию можно пометить **общей** — её открывает любое устройство с доступом к серверу. После подключения сервера можно создать сессию на сервере и открывать с любого устройства, либо как раньше — локальную.

## 2. База: SQLite

Нужен полнотекстовый поиск → берём SQLite. Развилка — как получить шифрование на диске:

| Вариант | Один файл | Шифрование | FTS5 (поиск) | Чистый Go | Цена |
|---|---|---|---|---|---|
| **A. SQLCipher** (`mutecomm/go-sqlcipher/v4`) | да | страницы целиком (`PRAGMA key`) | да | **нет, cgo** | нужен gcc при сборке; бинарник +6–8 МБ |
| **B. modernc.org/sqlite** | да | только отдельные колонки AES-GCM | да, но **только по открытому тексту** | да | поиск придётся делать в памяти или по расшифровке |

Спайк выполнен (26.11, `tmp/spike_sql.sh`, `tmp/spike_sqlcipher.sh`), см. 2.1.

**Решение: A (SQLCipher + тег сборки `sqlite_fts5`).** Причина: FTS5 работает по зашифрованным
страницам как обычный SQL, весь текст (включая индекс) на диске закрыт. Вариант B держит FTS-индекс
открытым текстом — это не «защищённая БД», поэтому он остаётся только аварийным запасным путём.
cgo требует gcc **только при сборке** (в Docker или на VPS — gcc есть), пользователю уходит готовый
бинарник на amd64/arm64; линковка с libc обычная, статический вариант — проверю в этапе 7.

### 2.1 Результат спайка (факты)
- A (`go-sqlcipher/v4`, cgo): сборка ~4 мин, бинарник **7,3 МБ**; `PRAGMA key` + `INSERT` работают;
  FTS5 `MATCH 'secret'` → **1 совпадение** (с тегом `sqlite_fts5`; без тега модуль FTS5 не включён);
  `grep "hello secret text"` по файлу БД → **0** (данные зашифрованы).
- B (`modernc.org/sqlite`, чистый Go): сборка быстрая, бинарник **10,0 МБ**, FTS5 → 1; но файл
  читается `grep` целиком — шифрования нет.
- Вывод: берём A. Тег сборки `-tags sqlite_fts5` — обязателен, иначе поиск «молча» не работает.

## 3. Схема БД (структура = IndexedDB + новые таблицы)

Имена полей в `json` — ровно как в браузере (`src/storage/db.ts`), поэтому клиентский код и
`api.go` не переписываются: меняется только реализация `Store`.

```sql
meta(key TEXT PRIMARY KEY, value TEXT)            -- schema, serverId, createdAt

agents  (id TEXT PK, json TEXT, updated_at INTEGER)
sessions(id TEXT PK, json TEXT,                   -- json = запись как в IDB
         title_enc BLOB,                          -- заголовок, если шифруем колонкой
         owner_device TEXT, shared INTEGER DEFAULT 0,
         created_at INTEGER, updated_at INTEGER)
messages(id TEXT PK, session_id TEXT, seq INTEGER,
         json TEXT, role TEXT, created_at INTEGER,
         body_enc BLOB)                           -- текст сообщения
usage(agent_id TEXT PK, json TEXT)
queue(id TEXT PK, json TEXT), tokens(id TEXT PK, json TEXT),
morph(id TEXT PK, json TEXT), audit(id TEXT PK, json TEXT), servers(id TEXT PK, json TEXT)

devices(id TEXT PK, label TEXT, invite_id TEXT, created_at INTEGER,
        last_seen INTEGER, revoked INTEGER DEFAULT 0, key_hash BLOB)
invites(id TEXT PK, options TEXT,                 -- JSON: {conn,agent,anon} + что включено
        payload_enc BLOB, expires_at INTEGER,
        max_devices INTEGER, used INTEGER DEFAULT 0,
        created_at INTEGER, revoked INTEGER DEFAULT 0)
invite_uses(invite_id TEXT, device_id TEXT, at INTEGER)

CREATE INDEX idx_sessions_updated ON sessions(updated_at DESC);
CREATE INDEX idx_sessions_scope   ON sessions(shared, owner_device);
CREATE INDEX idx_messages_session ON messages(session_id, created_at);
CREATE VIRTUAL TABLE fts_message USING fts5(id UNINDEXED, body, tokenize='unicode61 remove_diacritics 2');
```

`messages.body_enc` дублирует текст из `json`: `json` — для клиента как есть, `body_enc` — если
понадобится поле-шифрование (вариант B). При A (SQLCipher) оставляем только `json`.

Миграция: при старте, если `meta.schema` пусто, а `data/sessions/*.json` есть — импорт в SQLite,
каталог → `sessions.migrated-<дата>`. `meta.schema = 3`.

## 4. Шифрование на диске

- Вариант A: ключ страниц из `data/keys/db.key` (32 байта, 0600, создаётся при первом старте),
  `PRAGMA key`, `PRAGMA cipher_memory_security = ON`. Переопределение — `GENA_DB_KEY_FILE`.
- Вариант B: AES-256-GCM по колонкам `*_enc`, AAD = `table|column|rowID`.
- **Потеря ключа = потеря данных**: бэкап `gena.db` + `db.key` вместе, предупреждение в README,
  `AGENT_INSTALL.md` и в выводе `gena-server init`.
- `gena-server backup <файл>` — `VACUUM INTO` в копию (для A копия тоже зашифрована).
- `gena-server compact` — `VACUUM` раз в месяц по таймеру.

## 5. Передача: шифрованный конверт поверх HTTP

TLS на своём сервере часто нет, поэтому данные шифруем сами.

- PSK (32 байта) выдаётся в приглашении; из него HKDF → `c2s`, `s2c` (соль — `serverId`).
- Запрос: `X-Gena-Dev`, `X-Gena-TS`, `X-Gena-Nonce`; тело AES-256-GCM, AAD = `method|path|ts|nonce|deviceID`.
  Тег GCM = аутентификация устройства, Bearer-токен не нужен.
- Ответ: тело в ключе `s2c`, свой nonce в заголовке.
- Replay: окно ±120 с, nonce в LRU на 5 минут.
- `GET /api/health` открыт: `{serverId, version, enc:"v1", features:[...]}` — проверка адреса до пары.
- На каждое устройство — свой ключ (PSK + deviceID → HKDF), поэтому отзыв одного не рвёт остальные.

## 6. Приглашения: код, QR, содержимое

Запись `invites` создаётся админом:

```bash
gena-server invite --label laptop --ttl 15m --devices 3 \
  --with conn --with agent --with anon \
  --delivery both            # code | qr | both
```

- `--with conn` — подключение к серверу (URL, serverId, PSK) — обязательная часть, если клиент ещё не подключён.
- `--with agent` — данные агента для быстрых вставок: протокол, baseUrl, модель, параметры
  (ключ провайдера — по флагу `--include-agent-key`, по умолчанию **нет**).
- `--with anon` — предустановка «анонимайзер включён» для добавляемого подключения.
- Любая комбинация: все три, две или одна (кроме `agent`/`anon` без `conn` — при отсутствии
  подключения клиент предложит применить настройки к текущему серверу).
- `--ttl` — срок действия приглашения (по умолчанию 15 мин, максимум 30 дней). После истечения
  `POST /api/pair` → `410 invite_expired`, клиент пишет «сервер не поддерживает это приглашение».
- `--devices N` — сколько устройств можно подключить по этому приглашению (`used`), каждое = один
  пользователь; исчерпано → `403 invite_exhausted`, приглашение закрывается автоматически.
- Одноразовое использование не обязательно: приглашение живёт до TTL/лимита, `--single` для одноразового.

Код: `gena1:<base64url(JSON)>`, JSON = `{v:1,u,sid,k,e,lbl,opts:{conn,agent,anon},max}`.
QR: тот же текст → PNG (`invite-<id>.png`) + печать в терминале + страница `/pair` (под админ-токеном).
`--delivery code` печатает только код, `qr` — только QR/PNG, `both` — и то, и другое.

Клиент: в «Подключения → Добавить сервер Gena» три способа — вставить код, навести камеру
(BarcodeDetector, Chromium), либо открыть `/pair` на сервере и отсканировать. После пары:
если в коде есть `agent` — форма агента предзаполняется; если `anon` — переключатель включается.

## 7. Устройства и доступ

- `gena-server device list` — id, метка, приглашение, последний раз, статус.
- `gena-server device revoke <id>` — сброс токена клиента вручную (админ); клиент получает
  `401 {"error":"revoked"}` и предлагает подключиться заново.
- `gena-server invite revoke <id>` — закрыть приглашение (новые устройства не подключатся).
- На клиенте подключение удаляется вручную (в «Подключениях»), с опцией «сообщить серверу»
  (`DELETE /api/devices/self`) — иначе запись остаётся в списке админа как «не заходило N дней».
- Видно в `/pair`: активные приглашения (TTL, used/max), устройства, кнопки «сбросить», «отозвать».

## 8. Сессии: общие и локальные

- `sessions.shared = 1` → открывается любым устройством сервера; иначе только `owner_device`.
- `GET /api/sessions?scope=mine|shared|all` — клиент показывает вкладки в диалоге «＋ серверная сессия».
- `POST /api/sessions {title, shared}` — создать на сервере (в т.ч. «общую»).
- `PATCH /api/sessions/{id} {title?, shared?}` — пометить общей/личной (владелец или админ).
- В `Session.serverId` уже есть признак «серверная»; добавляем `shared?: boolean` и в клиентское
  хранилище (IndexedDB v9, миграция без потери данных), бейдж «Общая» в списке и в шапке чата.
- Локальные сессии остаются как были: `serverId` пустой, синхронизация не идёт.

## 9. Поиск по сообщениям

- `GET /api/search?q=&scope=mine|shared|all&session=&limit=50&before=` — FTS5 (`MATCH` + `snippet()`),
  сортировка по `created_at DESC`, курсор `before` для «показать ещё».
- Видимость: ищем только по сессиям, к которым у устройства есть доступ (свои + общие).
- Клиент: в существующем поиске по чату — секция «на сервере» (если сервер подключён), переход к сообщению.
- Вариант B (если SQLCipher не соберётся): индекс в памяти, строится при старте из расшифрованных
  строк (`id, session_id, body`), поиск подстрокой с подсветкой. Для 100 тыс. сообщений это ~30–40 МБ RAM.

## 11. Критерии готовности

1. `data/gena.db` — единственный файл данных; `grep` по нему не находит текста сообщений.
2. Пустой каталог → старт; старые JSON мигрируют, старые диалоги открываются.
3. Приглашение: код и QR; подключение по обоим путям; в коде можно включить conn/agent/anon в любой комбинации.
4. Лимит устройств и TTL работают: третий клиент при `--devices 2` получает отказ, после TTL — `410`.
5. Админ сбрасывает токен → устройство теряет доступ; удаление подключения на клиенте работает.
6. Общая сессия видна и открывается с другого устройства; личная — нет.
7. Поиск: `q` находит сообщение в общей сессии у другого устройства, в личной — нет.
8. `go test ./...` зелёный, `npm test` 748+ зелёный, `vite build` и `vue-tsc` чистые.

## 12. Риски

- **cgo на машине сборки**: проверено — gcc есть, собирается за ~4 мин, бинарник 7,3 МБ. Для чужих
  машин собираем в Docker и раздаём готовый бинарник; требование «только gcc при сборке» пишем в README.
- **FTS5 включается тегом `sqlite_fts5`** — без него поиск не работает и ошибка неочевидна
  (`no such module: fts5`). Тег прописываем в Makefile/CI/install-скрипте и проверяем тестом,
  который падает, если `fts5` недоступен.
- **Потеря `db.key`** — данные нечитаемы; поэтому бэкап пары файлов и предупреждения в трёх местах.
- **FTS5 + шифрование**: индекс живёт в том же зашифрованном файле (A) — утечки нет; при B индекс в памяти.
- **Анонимайзер**: в этом релизе — только флаг/предустановка в приглашении. Сам прокси-режим (запросы к провайдеру через сервер) — отдельная задача, если нужен.
- **QR-камера** — только Chromium; вставка кода остаётся основным путём.
- **Долгий TTL на устройство** — если понадобится «срок жизни устройства», это отдельный столбец `devices.expires_at` (сейчас не делаем).
